The one-sentence version
On ACCS the Commerce core is locked — no PHP modules, plugins, observers or custom tables — so an “extension” is an out-of-process Adobe App Builder application that adds admin screens through the Admin UI SDK, stores its own data in App Builder’s database, and reaches the storefront through API Mesh.

1 · Why ACCS extensions are different

Adobe Commerce as a Cloud Service (ACCS) is SaaS. Unlike Adobe Commerce on-prem or on PaaS/Cloud, you do not get to deploy PHP into the Commerce runtime.

What you cannot do

  • No custom PHP modules, plugins or preferences
  • No observers / events.xml in-process
  • No custom MySQL tables or db_schema.xml
  • No adminhtml controllers, UI-component grids or layout XML
  • No SSH / filesystem access to the core

What you do instead

  • Build an Adobe App Builder app (serverless, out of process)
  • Add admin screens via the Admin UI SDK (React + Spectrum)
  • Persist data in App Builder Database (DocumentDB) + State
  • Talk to Commerce via REST/GraphQL and Adobe I/O Events
  • Feed the storefront (Edge Delivery) through API Mesh

The mental shift: an extension is no longer code that runs inside Commerce — it is a companion application that runs beside it and integrates over well-defined seams (SDK, events, APIs, mesh). This is more work up front, but it decouples your customisation from Adobe’s upgrade cadence.

Reference case — Menu Manager
The legacy ScandiPWA MenuOrganizer (80 files, 3 MySQL tables, 13 adminhtml controllers, 2 observers, 1 GraphQL query) was rebuilt for ACCS as a single App Builder app: a document database instead of tables, ~13 Runtime actions instead of controllers, an Admin UI SDK React SPA instead of adminhtml grids/forms, and event-driven reconciliation instead of observers.

2 · The architecture at a glance

Business logicAdobe I/O Runtime actions (Node.js)CRUD, validation, auth. One action ≈ one endpoint.

Commerce integrationREST / GraphQL · Adobe I/O EventsRead catalog/CMS; react to catalog changes (reconciliation).
StorefrontAPI Mesh → Edge Delivery Services blocksExpose a stable GraphQL field the storefront consumes.

Two contracts you will hear about

  • Admin UI SDK v1 — the older commerce/backend-ui/1 + a registration action. Deprecated for GA ACCS.
  • Admin UI SDK v2 — commerce/backend-ui/2 (a React SPA) plus commerce/extensibility/1 (App Management). GA ACCS only accepts v2. Build v2 from the start.

3 · Prerequisites

  • An ACCS instance (provisioned by Adobe) and an Adobe org that owns it. Note the region, instance id, Admin URL and GraphQL endpoint.
  • Adobe Developer Console project + workspaces (Stage / Production) with App Builder and required APIs (I/O Management, Events, App Builder Database, IMS S2S).
  • aio CLI (@adobe/aio-cli) and Node.js ≥ 22.22.
  • An OAuth Server-to-Server credential (for the app to mint its own service token).
  • For the storefront path: an Edge Delivery site and an API Mesh.
Governance
The app must live in the same Adobe org that owns the ACCS tenant, or App Management will never surface the extension in that instance’s Admin. Distribution stays first-party (Associate → Install to this instance); nothing is published to a public marketplace.

4 · Step-by-step build

4.1 · Scaffold the App Builder app

Initialise the project and select your Console workspace. Provision the database region.

aio login
aio app init            # or clone a boilerplate; pick org / project / workspace
aio app use -g          # bind the workspace
aio app db provision --region emea

4.2 · Model the data (system of record)

Put the schema and all pure logic (tree building, ordering, validation) in dependency-free modules so they can be unit-tested without Adobe access. The document database is the source of truth; State is only a cache (it caps TTL and can skip/duplicate keys mid-iteration, so never treat it as durable).

4.3 · Write Runtime actions (the API)

One action per operation (menu-list, item-save, …). Secure admin actions with require-adobe-auth: true and declare every credential the action needs as an input — a deployed action cannot read .env through process.env.

# ext.config.yaml (per action)
item-save:
  function: actions/item/save.js
  web: 'yes'
  runtime: nodejs:22
  inputs:
    IMS_OAUTH_S2S_CLIENT_ID: $IMS_OAUTH_S2S_CLIENT_ID
    IMS_OAUTH_S2S_CLIENT_SECRET: $IMS_OAUTH_S2S_CLIENT_SECRET
    IMS_OAUTH_S2S_ORG_ID: $IMS_OAUTH_S2S_ORG_ID
    IMS_OAUTH_S2S_SCOPES: $IMS_OAUTH_S2S_SCOPES
    AIO_DB_REGION: $AIO_DB_REGION
  annotations: { require-adobe-auth: true, final: true }

4.4 · Build the Admin UI (SDK v2)

Declare the app in app.commerce.config.ts and generate the two extension points. The admin screen is a React 19 + Spectrum S2 single-page app mounted with createExtensionApp.

// app.commerce.config.ts
export default defineConfig({
  metadata: { id: 'scandiwebmenumanager', displayName: 'Scandiweb Menu Manager', version: '1.0.0' },
  adminUi: { menu: { id: 'ScandiwebMenuManager::menu_manager', label: 'Menu Manager', pageTitle: 'Menu Manager' } }
});

The SPA calls your own actions with the admin’s IMS token from useIms(). Two headers are required by require-adobe-auth:

headers: {
  Authorization: `Bearer ${imsToken}`,
  'x-gw-ims-org-id': imsOrgId,     // both, or the gateway rejects the call
}

4.5 · Install it into the Admin

Deploy, then in the Commerce Admin go to Apps → App Management → Associate App (pick project + workspace) → Install. Both steps (Enable Admin UI SDK + Register Extension) must go green; the menu then appears in the Admin nav.

4.6 · Wire the storefront (optional)

Expose a read action, put a stable GraphQL field in front of it with API Mesh (a programmatic fetch resolver works; keep the shared secret in the mesh, never forwarded from the caller), and consume that field from an Edge Delivery block. Keep the payload flat — Mesh caps query depth — and rebuild any tree client-side.

4.7 · React to Commerce changes (optional)

Subscribe to Adobe I/O Events (e.g. category saved/deleted) and reconcile in an async action. Treat events as hostile: at-least-once, out of order, retried; dedupe on event id in State and return 5xx to trigger Adobe’s retry.

5 · Hard-won platform gotchas

Each of these cost real debugging time on the Menu Manager build and is not documented anywhere obvious.

TrapFix
Deployed action returns 500 but works locallyIt can’t see .env. Declare every credential as an action input.
The v2 SPA renders a blank page / jsxDEV is not a functionaio builds Parcel in development mode (emits jsxDEV) while NODE_ENV=production pulls production React (no jsxDEV). Deploy with NODE_ENV=development aio app deploy --force-build so both halves agree.
missing x-gw-ims-org-id headerAdmin calls need both the Bearer token and x-gw-ims-org-id (from useIms()).
Module Runtime: Needs to be within an iframe! + spinnerThe Admin UI SDK page only runs inside the Admin’s own iframe/shell context — not a standalone URL and not the generic custom-apps dev harness (which supplies a token but not the org id).
DocumentDB findOne throws “Document not found”It throws where Mongo returns null. Normalise to a findOneOrNull helper — and keep your test fake throwing too, so it can’t hide the bug.
aio app db provision then deploy fails on “must have packages”Provision writes a runtimeManifest.database block without packages. Add an empty packages: {}.
Admin UI SDK v2 has no localhost dev loop for ACCSEvery iteration is a deploy (~35 s). Budget for it; verify in the real Admin, not a local harness.
React Spectrum S2 styling breaks under a plain bundlerBuild the SPA inside the real web-src scaffold (Adobe’s pipeline), not a side project.
Storefront doesn’t reflect an edit immediatelyAPI Mesh caches GET responses by query key; edits appear after the cache TTL. Verify with the live action if you need certainty.

6 · Testing & deployment

  • Unit tests on the pure modules (schema, tree logic) — fast, no Adobe access. These cannot catch platform divergence.
  • Smoke tests against a real workspace/database — the only thing that catches DocumentDB/State behaviour. Run them before calling any change done.
  • Storefront tests (jsdom) on the Edge Delivery block’s tree-rebuild logic.
  • Deploy: NODE_ENV=development aio app deploy --force-build; re-create DB indexes in a post-deploy hook.
  • Verify in context: open the extension through the real Commerce Admin (Apps → your app), not a direct URL.

7 · Time needed for a similar module

Forward estimate of active AI build time for another Menu-Manager-class extension — admin CRUD UI + storefront rendering + optional event sync — now that the platform is known.

Each phase includes a generous buffer for review and iteration. Assumes the ACCS instance, Adobe Console workspace and API Mesh already exist (no re-provisioning) and a comparable scope.

PhaseActive build time
(active build, buffered)
Data layer — schema, pure logic, unit tests3–4 h
Backend CRUD actions + auth (require-adobe-auth, IMS)3–4 h
Storefront read path + API Mesh~2.5 h
Admin UI SDK v2 SPA — tree, grid, edit page, pickers8–10 h
App Management install + in-Admin verification~2.5 h
Storefront rendering (Edge Delivery block / mega-menu)3–4 h
Event-driven catalog sync (optional)~2.5 h
Tests, verification, docs~2.5 h
Total active build≈ 28–32 h (~4 working days)

Assumptions

  • Platform already known — the §5 traps don’t need re-discovering
  • ACCS instance + Console workspace + API Mesh already provisioned
  • Scope comparable to Menu Manager (admin CRUD + storefront)
  • Buffer for review and iteration baked into every phase

What sets the clock

  • The deploy loop (~35 s each; no local admin dev loop)
  • In-Admin verification of each screen
  • API Mesh cache TTL when checking the storefront
  • Coding itself is a small share of the total
Bottom line
With the platform known and the instance already provisioned, a similar module is about four working days of active build (≈ 28–32 hours, buffered). The one-time costs — provisioning and platform discovery — are already paid and do not recur; what remains is set by the deploy cadence and in-Admin verification, not by typing speed.

8 · Command reference

# Setup
aio login
aio app use -g
aio app db provision --region emea

# Build & deploy (v2 SPA needs NODE_ENV=development — see gotcha #2)
NODE_ENV=development aio app deploy --force-build

# Install into the Admin
Commerce Admin → Apps → App Management → Associate App → Install

# Verify the storefront read path (shared-secret protected)
curl -H "x-mm-secret: $SECRET" \
  "https://.adobeioruntime.net/api/v1/web/menu-manager/storefront-menu-get?identifier=main"

# Tests
npm test                 # pure unit tests, no Adobe access
npm run smoke            # assertions vs the REAL database
